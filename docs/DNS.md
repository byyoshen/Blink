# 为什么 IP 段要放在最后

配置 Blink 规则时，先放所有 App 的非 IP 段，再放所有 App 的 IP 段。
不要按「App A 域名 → App A IP → App B 域名」交错排列。

## 原因

域名规则可以直接按请求的主机名匹配。IP 规则需要目标 IP；客户端在尚不知道
真实 IP 时，可能先发起 DNS 查询。如果一个应走代理的域名先遇到会触发解析的
IP 规则，它就可能提前经过本地 DNS，影响 DNS 防污染和后续连接。

将非 IP 规则放在前面，可以让域名先确定路由。实际 DNS 查询发生在哪里，还取决于
客户端、Fake IP、代理协议和配置；仅仅调整规则顺序并不能替代正确的 DNS 设置。
对 CDN 服务来说，解析位置也可能影响分配到的节点与连接速度。

## 文件怎么选

同一 App 的非 IP 段只会提供以下两种名称之一：

| 文件 | 内容 | Surge 引用方式 |
| --- | --- | --- |
| `<App>-domainset.conf` | 只有域名与域名后缀 | `DOMAIN-SET` |
| `<App>-nonip.conf` | 非 IP 规则，可能包含关键词或其他客户端支持的类型 | `RULE-SET` |
| `<App>-ip.conf` | IP 段；没有 IP 规则的 App 不提供 | `RULE-SET` |

上表的引用关键字针对 Surge。其他客户端的格式不同，sing-box 的视图文件为 JSON；
请在 [Blink 门户](https://blink.wendylala.com/) 选择自己的客户端后复制对应片段。
引用类型写错可能没有明显报错，却没有按预期分流。

## 添加时检查这三件事

1. 将所有已选 App 的非 IP 段放在所有 IP 段之前；门户生成的片段已按这个顺序排列。
2. 保留门户给出的引用类型、格式和客户端支持的 `no-resolve` 设置，不要跨客户端照抄。
3. 导入后查看客户端日志，确认目标 App 命中了预期规则和策略，而非仅确认下载成功。

`no-resolve` 在支持它的规则位置用于避免仅为匹配 IP 规则而触发 DNS 解析。
各客户端的能力和语法不一致，不支持的字段不能通过改名硬加。
